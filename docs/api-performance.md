# 経路APIの応答時間調査

2026-09-10に公開リファレンスとOpenAPIを確認し、東京→東金で実測した。調査後、駅間検索と徒歩の分離を実装した。具体的な上限・キャッシュ・フォールバック条件はREADMEの「駅間検索と徒歩」を参照。

参照: https://api.transit.ls8h.com/api/docs 、https://api.transit.ls8h.com/api/openapi.json

## 条件

- サービス日: 20260910。検索時刻: 14:30:00、追加検証は14:40:00。
- 東京座標: `geo:35.681,139.767`
- 東金座標: `geo:35.5602766,140.3636144`
- 東京駅ID: `scrape-jreast-sobu-rapid:odpt.Station:JR-East.SobuRapid.Tokyo`
- 東金駅ID: `scrape-jreast-togane:odpt.Station:JR-East.togane.s1038`
- `type=departure`, `allowModes=rail,subway,tram,monorail`, `numItineraries=3`
- curlによる逐次リクエストの実経過時間。API本体の処理時間とネットワーク時間の合計。サーバーキャッシュ状態は不明。

## 分かったこと

- `/plan` は座標とfeed-qualified駅IDの両方に対応する。今回、駅ID→駅IDは明確に速かった。
- 座標指定時の候補駅の探索などがコストになっている可能性がある。ただしサーバー内部は確認できておらず、処理箇所の断定はできない。
- `numItineraries` は返却候補数であり、探索量を必ず減らすという保証はリファレンスにない。
- `maxTransfers` を下げたり `avoidWalk=true` にすると利用可能な経路を除外するため、速度だけを理由に採用しない。
- `/guidance/plan` は推薦理由・地図・次の行動などの追加情報を返すAPI。高速版との記載はない。
- `/stations/{id}/departures` は出発案内で、乗換先までの到達可否は判定できない。ODPT由来の出発時刻表の公開にも制約があるため、経路検索の代用にしない。

## 採用した実装方針

駅の解決と鉄道経路の検索を分離し、現在地→候補駅、駅ID→駅ID、到着駅→登録住所を連結する。乗車駅に着く時刻を出発検索に渡し、最後の徒歩を到着に足す。当初は複数候補を比較していたが、2026-09-16の実API検証で同じ物理駅の異なる路線別IDから駅構内接続を通って経路を検索できることを確認した。現在は最寄りの物理駅を1つ選び、その駅の代表IDだけを検索する。利用できない場合は座標検索へ戻す。

今回使った駅IDは事前の座標検索結果から得ている。したがって0.24〜0.61秒は駅間検索のみの値であり、初回の駅候補解決と徒歩計算を含むアプリ全体の速度ではない。

駅候補・目的地側の徒歩情報は、目的地変更時や現在地の移動時に無効化するキャッシュで再利用できる。終電も日時と出発地が変わっていない短時間の再表示で再検索しない設計を検討する。GPSの揺らぎを許容する場合は徒歩出発期限に余裕を入れる必要がある。

## 実装後の確認

同じ東京・東金の座標で、実APIとApple MapKitを使用し、アプリと同じStationRouterをmacOSの検証用実行ファイルから2回実行した。2026-09-10の最終計測では、初回は駅・徒歩の準備0.91秒、通常経路取得まで合計9.04秒。同一地点の2回目は準備0.0002秒、通常経路取得まで合計1.29秒だった。東京の18個の路線別IDと東金1個から始め、2回目は実際に乗降した推奨駅の組み合わせを再利用した。

この値はGPS取得と終電検索を含まない。初回は8秒を上限に取得できた候補を比較するため、0.24秒の単一駅間リクエストと同じ速度にはならない。ネットワーク状態、Appleの徒歩計算、APIの応答により変動する。シミュレータ・実機の画面操作全体の測定値ではない。

その後のアプリ画面検証で、8秒までに返った候補だけを使うと東京→東金で甲府経由の大回りを選ぶケースが判明した。現在は比較のタイムアウト・通信失敗時に途中結果を破棄し、座標検索へ戻す。上記の初回9.04秒は修正前の値であり、現在の初回処理時間を示すものではない。座標検索で確認した実際の乗降駅IDを次回再利用する。

ビルドはiPhone/Widget/Watchの3ターゲットで成功。19件のテストで徒歩合算・駅候補比較・駅ID再利用・5分後の再比較・移動時の徒歩再計算・終電キャッシュ失効・深夜のサービス日・座標フォールバックなどを確認した。

追加修正後は21件の単体テストとiPhoneシミュレータ上のUIテストが成功した。UIテストは更新完了とエラーなしの経路表示、東京→東金で甲府経由を採用していないこと、再起動後の目的地・経路保持を確認した。位置取得は最初の古い測位を即座に失敗扱いせず、新しい測位を待って取得後に停止する方式へ変更した。
